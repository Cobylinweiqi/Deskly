# 上架 LSPosed 官方模块库

> 这一篇是给**维护者**看的操作备忘，普通用户不需要读。

LSPosed 的在线模块库（`modules.lsposed.org`）由 [Xposed-Modules-Repo](https://github.com/Xposed-Modules-Repo) 组织托管。上架之后，用户可以在 LSPosed 客户端的「在线仓库」里搜到 Deskly，一键安装、自动更新。**不上架也完全可以正常用**，只是每次更新得手动下 APK 覆盖安装。

## 一、包名与仓库现状（已完成）

- 应用包名已确定为 `io.github.cobylinweiqi.deskly`（满足官方 `io.github.<用户名>.*` 命名空间要求，无需配 DNS TXT 记录）。
- 官方模块库仓库已建好：`https://github.com/Xposed-Modules-Repo/io.github.cobylinweiqi.deskly`（提交时由 XposedBot 自动创建，并邀请维护者为协作者，权限 maintain / 可 push）。
- 已接受 XposedBot 的协作者邀请，具备向该仓库推送 Release 的权限。

> 历史：最初包名为 `com.coby.deskly`，不满足命名空间要求；后改为 `io.github.cobylinweiqi.deskly`（0.13.0 起）。**包名变更属于换包**，老用户需手动备份 → 卸载旧版 → 装新版 → 恢复。0.13.0 之后包名稳定，后续均为同包名覆盖升级。

## 二、首次上架提交流程（历史，已做过，留作参考）

1. 打开 <https://modules.lsposed.org/submission/>（会跳到一个预填好的 Issue 页面）；
2. 标题填 `[submission] <包名>`，例如 `[submission] io.github.cobylinweiqi.deskly`；
3. 提交后机器人会为这个包名建一个仓库并邀请你成为协作者；
4. 在**官方模块库仓库**里补上 README（仓库 description 因权限限制可能设不上，但不影响索引——索引器读的是 APK 的 manifest）；
5. **在两个仓库都发布附带 APK 的 Release**（见下一节）。

## 三、后续每次发版（双仓库 Release，缺一不可）

tag 格式固定 `<versionCode>-<versionName>`，例如 `21-0.13.0`。**`versionCode` 必须递增**，否则在线仓库认为"不是新版本"不触发更新。

也可以用一行脚本完成：`scripts/release.sh <versionCode> <versionName> [更新说明]`，例如：

```bash
./scripts/release.sh 22 0.14.0 "修复图标重排错位"
```

脚本会自动：改 `build.gradle.kts` 版本号 → 干净构建 → 主仓库打 tag 并发布 Release → 官方模块库仓库发布同 tag 的 Release。

手动步骤（与脚本等价）：

```bash
APK=app/build/outputs/apk/release/app-release.apk

# 0. 先改 app/build.gradle.kts：versionCode = 22、versionName = "0.14.0"

# 1. 干净构建
./gradlew clean assembleRelease

# 2. 主仓库：给用户手动下载 / 覆盖升级
git tag 22-0.14.0
git push origin 22-0.14.0
gh release create 22-0.14.0 "$APK" \
  --repo Cobylinweiqi/Deskly --title "0.14.0" --notes "更新说明"

# 3. 官方模块库仓库：被在线仓库索引（搜得到 / 自动更新的关键）
cp "$APK" /tmp/Deskly-0.14.0.apk
gh release create 22-0.14.0 /tmp/Deskly-0.14.0.apk \
  --repo Xposed-Modules-Repo/io.github.cobylinweiqi.deskly \
  --title "0.14.0" --notes "Deskly 0.14.0 —— 小米 / HyperOS 与真我 realme UI / ColorOS 桌面整理模块。源码与说明见主仓库。"
```

机器人会在 5~15 分钟内索引到新版，客户端即可搜到并一键更新。

## 四、几个容易踩的点

- **只改 Release 里的 APK 不会触发更新**，必须新建一个 Release（或至少修改 Release 内容触发 webhook）；
- 仓库名必须等于包名，description 不能空（官方仓库的 description 因权限设不上去，但索引器读 APK 的 manifest，影响有限），Release 里必须有 `.apk` 资产；
- **两个仓库都要发 Release**：主仓库只供人手动下；在线仓库索引读的是 `Xposed-Modules-Repo/<包名>` 仓库的 Release；
- **`versionCode` 必须比上一版本大**，且 tag 必须带 versionCode；
- **官方模块库仓库的 `description` 必须非空**（它就是模块显示名），且**只能在网页浏览器里设置**：
  REST `PATCH /repos/{owner}/{repo}` 与 GraphQL `updateRepository` 对 maintain 角色会返回 404 / FORBIDDEN
  （GitHub 权限矩阵里 maintain 能改 description，但 API 端点按 admin 校验；网页 About 齿轮可改）。
  空 description 会让索引器**完全跳过**该仓库；60 分钟倒计时是从"所有条件满足（含 description）"才开始。
- 项目源码**留在本项目**，官方那个仓库只放摘要与 README，不放代码。
