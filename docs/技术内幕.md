# Deskly · 技术内幕

> 这篇是开发笔记：每个问题怎么暴露、用什么手段定位（真机读库 / 快照对比）、根因在哪个文件的哪一行、
> 哪一版修掉。写给要改这份代码或者想弄清"它到底动了什么"的人。
> 想直接装来用，请回 [README](../README.md)。


LSPosed 模块框架，目标是让桌面自己整理成该有的样子。

当前版本 **0.12.4**：
- **整理桌面（主功能）** —— 一条直线：**分析桌面全部图标 → 选方案 → 预览并写入**。
  「分析」读一次桌面库，把文件夹内与散落的图标合成一批，同时按颜色与功能各归一次类；
  方案卡并排可点选，选中即重算分组与屏位；写入按钮放在固定底栏，滚到哪都能点。
  动手前自动拍快照；写完后桌面会重启一次，布局即刻生效
- **精细归位** —— 不动整体结构，只把散落和放错的图标挪进合适的文件夹，每条可改可取消
- **配置页** —— 两张卡默认**折叠**，点标题展开：**运行引导**（LSPosed / 作用域 / root / 重启桌面 / 电池优化，能查的写清状态、查不到的直说）与**备份与恢复**。收起时各露一行摘要（`5 步 · 就绪 3` / `4 份备份 · 最近 16:05`），不展开也知道什么状态。原来的「运行状态」「诊断」「探针报告」全部移除
- **备份与恢复** —— 改坏之后能退回去的唯一保障。每份备份可展开到**每个图标**：哪个应用在哪个文件夹、文件夹在第几屏第几格；恢复直接用选中的快照覆盖，**不再额外备份当前状态**
- 两个预设方案（方案一按颜色 / 方案二按功能）+ 分组明细 + 屏号可调 + **第一屏留空**
- **root 失败原因可区分**（未授权 / Magisk 守护进程挂了 / 没有 su / 等授权超时）
- **root 到手后仍读不到桌面库**（App 的挂载命名空间隔离）—— 0.9.0 修复
- **写完不生效**（杀了桌面又等一秒，系统正好把桌面拉起来读旧库）—— 0.10.0 修复，
  见「第五种：写入全返回成功，桌面却一点没变」
- **钉到第 6 屏却跑到第 2 屏**（把旧文件夹自己占的格位当成障碍物，新布局只能往缝里塞）—— 0.11.2 修复，
  见「第七种：钉到第 6 屏，跑到了第 2 屏」
- **整理好了却报"整理失败"**（写完之后对着真库重算 sha256 当失败判据，而桌面启动后
  一定会自己改库）—— 0.11.1 修复：写入核对挪到灌库那一刻，成败改由**回读真库数落位**
  判定，见「第六种：桌面已经整理好了，界面却报失败」

界面按两页分工：**整理**（三步一条线：分析 / 选方案 / 预览并写入，精细归位折叠在页尾）
与 **配置**（运行引导 + 备份与恢复）。备份是"动手之前"要确认的事，排在分类结果最底下时想拍张快照得先划过整页。

> **0.11.0 重排了首页的信息层级。** 0.10.x 的首页是五张等重白卡平铺（整理桌面 / 方案 /
> 分组明细 / 精细归位），分析、选方案、写入三个动作混在一起，方案只是一行文字，
> 能不能点全靠猜。现在按动作顺序拆成三步，方案做成并排两张带视觉预览的卡片，
> 「精细归位」降级为页尾折叠区——它是整理之后的微调，不该和入口抢注意力。
>
> 一个如实说明：分析范围是**桌面上已有的图标**（含文件夹内）。`favorites` 写库只挪已有条目，
> 不会把"装了但没放到桌面"的应用塞进来；这种应用有多少个，界面会直接写出来。

> **0.10.0 改过一次功能定位。** 0.9.0 的首屏第一张卡是「图标归位」，它只处理散落和放错的
> 图标——真机 155 个图标里只有 5 个会出现在待办列表里，于是"整理桌面"这件事被呈现成了
> "处理 5 个散落图标"。现在首屏第一张卡是「整理桌面」：整张桌面按方案重排，全部图标都参与。

## 前置条件

| 项 | 要求 |
|---|---|
| 设备 | 已 root（备份与归位都需要），已装 LSPosed（**API 101**，即 LSPosed 1.10+ / Vector 2.x） |
| 系统 | Android 8.0+（minSdk 26） |
| 默认目标 | `com.miui.home`（小米桌面 / HyperOS） |

> 如果 LSPosed 管理器提示 `minApiVersion` 不满足，说明你的框架 API < 101。告诉我版本号，我出一个 API 93 的兼容分支。

## 装与启用

1. `adb install -r Deskly-0.9.0.apk`（或直接点 APK 安装）
2. 打开 LSPosed 管理器 → 模块 → 勾选 **Deskly**
3. 作用域里勾选 **`com.miui.home`**（其它桌面自己加）
4. 让模块生效：设置 → 应用 → 小米桌面 → 强行停止，或直接重启手机
5. 打开 Deskly → 切到「配置」按「运行引导」走完（LSPosed / 作用域 / root / 重启桌面）→ 回到「整理」点「分析桌面全部图标」

> **归位不依赖 LSPosed 注入**。它走的是 root 直改数据库这条路，所以即使模块还没生效、
> 作用域还没勾，归位也能用。第 2–4 步是给"方案与分屏布局"的未来写入层准备的。

## root 失败：三种完全不同的原因

0.6.0 及以前，`Shell.hasRoot()` 只返回一个布尔值，于是四种情况在界面上长得一模一样，
全都显示"未获得 root"。真机上就吃了这个亏：用户在 Magisk 里明明点了允许，界面还催他去授权，
因为真正坏掉的是 magiskd，跟授权毫无关系。

现在改成 `Shell.probe()` 返回 `Probe`，按原因分开：

| kind | 判据 | 该做什么 |
|---|---|---|
| `OK` | 退出码 0 且 `id -u` 输出 `0` | — |
| `DENIED` | su 跑起来了，但没拿到 root | 去 Magisk 里授权 |
| `DAEMON_DOWN` | 输出含 `Cannot connect to daemon`，或退出码 133（信号 5） | **重启手机** |
| `NO_SU` | 进程根本没起来（ENOENT / EACCES） | 这台设备没有 root |
| `TIMEOUT` | 90 s 内没有回应 | 授权框被折叠成通知了 |

`DAEMON_DOWN` 是怎么认出来的：Magisk 的 CLI 是 Rust 写的，连不上 magiskd 的 socket 时
它先打印 `Cannot connect to daemon: Connection refused (os error 111)`，随后 panic abort——
进程以信号 5（SIGTRAP）终止，Java 侧拿到的 `exitValue()` 是 `133`。所以
"退出码 133 或那句原文"就是守护进程死了的签名，和"没授权"是两件完全不同的事。

守护进程只在开机时由 Magisk 的 post-fs-data 脚本拉起，应用没法重启它——拉起它本身就要 root，
而这时 root 已经不可用。所以唯一的恢复动作是重启手机，重启后所有需要 root 的应用一起恢复。

配套的两个行为改动：

- **回到前台自动重查**（`BackupSection.recheckIfDegraded()`，仅在上次失败时触发，节流 8 秒）。
  用户去 Magisk 点允许再切回来，状态自己会变，不用再去另一个 tab 底部找「重新检测」。
  节流是必要的：授权方式若是"每次询问"，来回切页面会连环弹框。
- **整理页顶部直接说原因**：root 坏掉时首页就摆出 `Magisk 守护进程没有运行 · 重启手机可恢复`，
  而不是等用户点「分析散落图标」才蹦出一句含糊的"需要 root"。这条告警与"没找到小米桌面"
  各自独立判断，可以同时显示。

## 第四种：root 拿到了，却读不到数据库

0.9.0 修掉的那个问题，比前面三种都隐蔽，值得单独记一笔。

**症状**：`su -c 'id -u'` 返回 `0`（确实是 root），但紧跟着
`ls /data/user_de/0/com.miui.home/databases` 返回 `No such file or directory`。
同一时刻用 `adb shell` 跑同一条命令，20 多个文件列得好好的。

**根因**：Android 11 起，每个 App 进程有**独立的 mount namespace**，别的 App 的数据目录
在里面根本没被挂载。Magisk 的 su 默认继承调用者的 namespace（"Inherited" 模式），
所以 App 内的 root 虽然拥有最高权限，却**看不见**目标路径——不是没权限，是那个挂载点不存在。

验证方式（用 root 进入 App 的命名空间亲眼看）：

```sh
PID=$(pidof com.coby.deskly)
su -c "nsenter -t $PID -m -- ls /data/user_de/0/com.miui.home/databases"
# → No such file or directory
su -c "nsenter -t 1 -m -- ls /data/user_de/0/com.miui.home/databases"
# → 正常列出 launcher4x6.db 等
```

**为什么特别容易误判**：报的是 `ENOENT` 而不是 `EACCES`。所以它看起来像"路径猜错了"
或"这个 ROM 把库放在别处"，而不会让人想到权限——毕竟 `id -u` 已经证明是 root 了。
我第一轮排查就先去改选库逻辑，方向是错的。

**修复**：`Shell.su()` 统一把命令搬进 init 的全局命名空间执行：

```sh
nsenter -t 1 -m -- sh -c '<原命令>'
```

`nsenter` 在 toybox 里（`/system/bin/nsenter`，App 的命名空间里也可见）。
`Shell.nsState()` 先探一次 `nsenter -t 1 -m -- true`，不通就退回原命令；
若探测失败的原因是"还没授权"这类，**不缓存**结论——否则一次太早的探测会把后续
所有命令永久钉死在错误路径上。

**顺带暴露的第二个坑**：修好命名空间之后，`/data/data/com.miui.home/databases`
里只有 `onetrack_cache.db`（**6.2 MB**），而真库 `launcher4x6.db` 只有 122 KB 且在
`/data/user_de/0/` 下。旧逻辑"第一个目录非空就不看第二个"会直接漏掉真库；而如果
退回"取最大的 .db"，又会选中那个 6 MB 的分类缓存。现在两个目录一次列全、按
`launcher*` 前缀优先、取最大仅用于同级候选之间挑。

**为什么"诊断页的重新分析能跑"**：它调的是 `AppClassifier.loadDesktopVisible()`，
只用 PackageManager 列应用，**从不读数据库**，所以它本来就不受这件事影响。
两个按钮长得像，做的事完全不同——这也是把它拆成两页之后反而更容易误导的地方。

## 第五种：写入全返回成功，桌面却一点没变

这是 0.10.0 修掉的那个，也是唯一一个**不报错**的故障：`am force-stop` 返回 0、`cat` 返回 0、
摘要校验也一致，界面上写着"完成"，桌面却原封不动。

根因是原来那条命令里的 `sleep 1`：

```sh
am force-stop com.miui.home ; sleep 1
rm -f launcher4x6.db-wal launcher4x6.db-shm
cat <改好的库> > launcher4x6.db && sync
```

1. force-stop 把桌面杀了，**但系统把它当 HOME，几百毫秒内就会重新拉起**；
2. `sleep 1` 正好让新进程在这个窗口里完成启动，**打开的还是旧库**；
3. 我们随后 `cat` 覆盖，改的是同一个 inode，可新进程早把布局读进内存，不会因为文件变了就重读；
4. 桌面此后随便写点什么，就把内存里的旧布局刷回库——改动连痕迹都不剩。

**修复**（`core/DbInject.java`）：杀 → **轮询 `pidof` 等它真的没了** → 写 → **再杀一次**。
第二刀是关键：此时库里已是新数据，系统再拉起桌面，读到的就是新布局。最后补一个
`input keyevent 3`，桌面立刻回前台，用户不用自己找。

回执里带 `gone=[pid]`：非空说明写入那一刻桌面进程其实还活着，这次多半不会生效——
把这件事透给用户，比让人对着"成功"发呆强。恢复快照走的是同一条路径（`BackupStore.restore`），
所以**以前"恢复了但看起来没变"也是同一个 bug**。

## 第六种：桌面已经整理好了，界面却报"整理失败"

0.11.1 修掉的那个。真机上点「应用方案」之后，桌面确实按方案分好了文件夹、排好了屏，
可对话框标题写着**整理失败**，正文还劝用户"用快照 XXX 回滚后重试"。照做就等于把刚整理好
的桌面亲手撤销。

根因是 `DeskWriter` 写完之后多做了一道校验：

```java
// 0.11.0 的写法（错的）
Shell.su("sha256sum <真库>");          // 拿它和写进去的那份副本比
if (!got.equalsIgnoreCase(workSha)) {  // 对不上就判失败
    r.msg = "已写入但摘要不一致，请用快照回滚后重试";
}
```

问题在**比对的时机**：`DbInject` 的最后一步是 `input keyevent 3` 把桌面拉回前台。
Launcher 一起来就会自己打开这个库——补字段、合并 WAL、还原它自己的东西——几秒后主库
字节必然和当初 `cat` 进去的那份不同。**摘要不同是正常现象，不是失败。**

修复（`backup/DeskWriter.java`、`backup/LayoutWriter.java`）：

1. 删掉"写完后比真库 sha256"这道判据。真正的写入核对留在 `DbInject` 内部——`cat` 完
   立刻 `stat` + `sha256sum`，那个时刻桌面还没开始读库，比才是有效的。
2. 成败改由**语义回读**判定：等 900ms 再 pull 一份真库，数一遍"有多少图标落在我们新建 /
   复用的那些 container 里"。桌面爱怎么改自己的字段都行，成员在哪个 `container` 就是布局本身。
   回读不符不直接判失败，只在回执里写 `⚠ 回读只有 N/M`，让人先看一眼桌面再决定。
3. 界面区分两种失败：`wrote == false` 才叫「整理失败」；`wrote == true` 但核对没过，标题是
   「已写入，但有对不上的地方」，并且清掉旧的预览与计划——否则用户以为没生效，再点一次写入
   就会拿一份基于旧桌面的计划把刚整理好的结果改写掉。

## 第七种：钉到第 6 屏，跑到了第 2 屏

0.11.2 修掉的那个。真机数据摆在这里（整理前后各拉一份库对比）：

| 整理前 | 该屏文件夹占的候选位 | 被算成"还空着"的位 | 结果 |
|---|---|---|---|
| 第 2 屏 | 2、3、4、5 | 只剩 0、1 | 第 2 屏只排得下 **2** 个 |
| 第 3 屏 | 2、3、4 | 只剩 0、1、5 | 排 3 个 |
| 第 4 屏 | 0、1、2 | 只剩 3、4、5 | 新文件夹被排到 `(2,2)(0,4)(2,4)` |

整理后的实际坐标和"只剩这些位"一一对上——**每个旧文件夹都把自己当前占的 2×2 洞，当成了不能用的障碍物。**
可这些文件夹正是这次要挪走 / 删掉的东西。

根因在 `DeskPlan.build` 收集"原地不动"清单的那一步：

```java
// 0.11.2 之前：文件夹本体（itemType=21）也被算进了 stayPut
for (DesktopModel.Item i : model.looseOnDesktop) {
    if (i.isApp()) apps.add(i);
    else plan.stayPut.add(i);        // ← 文件夹也进来了
}
```

`stayPut` 是喂给 `slotsOf()` 算"哪些格位被小组件压住"的。文件夹一进来，每个文件夹就把自己
现在的位置标成"已占用"，新布局只能塞进旧布局剩下的缝里。两个后果：

1. **每整理一次，分组就摊得更散、屏数越排越多**（capacity 从 6 掉到 2~3）；
2. **预览和写入必然对不上**——预览用的是分析那一刻的旧位置，写入时又重新拉一次库、重新算一遍
   障碍物。桌面在这中间自己挪过文件夹，两边的"空位"就不一样，于是预览说第 6 屏、写进去是第 3 屏。

修复：

- `stayPut` 只收**真正不动**的东西（小组件、桌面上的系统入口），文件夹一律排除。
  去掉之后，格位只受小组件影响，而小组件本来就不随整理移动——**预览与写入从此用同一份"障碍物"**。
- `LayoutPlan` 新增 `spillOverflow()`：钉屏把某一屏塞爆时，放不下的顺延到下一屏，而不是写到
  `cellY=6` 这种 4×6 桌面根本不存在的格子上（`slotOf()` 对越界索引是原样返回的，桌面读进去只会
  把它随手挪走）。
- 回读时顺带核对**每个文件夹的屏号**，不一致直接写进回执：
  `⚠ 屏号和计划不一致：摄影 计划第3屏→库里第2屏`。以后再出现这类偏差，一眼能看出是"我们没写对"
  还是"桌面把它挪了"。
- 分组行上的屏号胶囊在"钉了但没排到那一屏"时显示成 `第 3 屏（钉 6）`，不再只显示其中一个。

## 整理桌面（0.10.0 的主功能）

| 做法 | 行为 | 这一版 |
|---|---|---|
| **整理** | 打散全部图标，按方案重新建文件夹、重排屏位 | **做了**，首屏第一张卡 |
| **归位** | 保留已有文件夹，只调整"位置不对"的图标 | 做了，退到页面最下面的「精细归位」 |

0.9.0 只做了归位，理由是"用户的分类是长期积累的成果，机器重排一次就全毁了"。
这个判断被真机效果否掉了：**待办列表里永远只有 5 行**，因为 155 个图标里 146 个已经在文件夹里，
用户看到的是"它只处理散落的那几个"，"整理桌面"这个诉求根本没被满足。归位不是错，是太小。
现在两条都留着，但层级倒过来：整理是主功能，归位是整理之后的手工微调。

一次整理会做什么（真机数据：151 个应用图标 / 18 个文件夹 / 6 屏）：

| 步骤 | 结果 |
|---|---|
| 按方案分组 | 151 个 → 11 组（社交 11 / 影音 18 / 游戏 11 / 购物 11 / 金融 30 / 出行 4 / 生活 11 / 办公学习 7 / 工具 29 / 开发·Root 16 / 摄影 4） |
| 排屏 | 第 1 屏 4 个（被 4×2 日历压掉两个位）、第 2 屏 6 个、第 3 屏 1 个 |
| 文件夹 | 复用 5 个同名旧文件夹（购物/出行/影音/开发·Root/工具），新建 6 个，删掉 13 个空掉的 |
| 桌面上 | 只剩 1 个小组件 + 11 个文件夹，6 屏收到 3 屏 |

### 分类词典是被真机数据打回来重做的

初版词典只有几十条通用规则，拿真机 151 个图标一跑，**86 个落进「其它」**——整理完会是
"一个 86 个图标的巨型文件夹 + 一堆三四个的小组"，比用户自己分的还乱。功能没错，是词典太薄：
国内主流 App 和小米系统应用几乎全在词典外。现在的表按真机出现的包名逐条补齐（EXACT 190 条 +
HINTS 关键词），「其它」降到 0。

`开发·Root` 单独成组不是给所有人准备的，而是这类工具分散在"工具"里时，翻文件夹比翻桌面还慢。

### 三个来自真机数据、不能凭 Launcher3 印象改的约束

| 约束 | 真机证据 | 违反的后果 |
|---|---|---|
| 文件夹成员的 `screen` 必须是 **-1** | 147 条成员无一例外 | 写 0 或父屏号会被判为非法项 |
| 成员位置 = `cellX`（组内序号）+ `cellY`（序号/4） | 16 个成员的文件夹正好 cellX 0..15、cellY 0..3 | 按网格坐标算会错位、互相覆盖 |
| 文件夹本体 `spanX=spanY=2`，一屏 4×6 只放 **6** 个 | 6 屏实测坐标 | 按 24 算会把第 5 屏的组摊到第 2、3 屏 |

### 小组件占的是具体格子，不是"少两个名额"

第 1 屏摆了个 4×2 的组合日历，压掉 `(0,0)` 和 `(2,0)` 两个文件夹位。
如果只把"这一屏的容量"从 6 减到 4，文件夹仍会被放进**前四个**候选位——正好撞上日历。
所以排布依据的是**剩哪几个具体位置**（`{2,3,4,5}`），不是"还剩几个"。
这个 bug 在离线仿真里抓到过一次：桌面上出现了 `(0,0) 组合日历` 和 `(0,0) 社交` 重叠。

### 不复用系统自动分类的文件夹

小米的「工具」「游戏」文件夹标题存的是资源引用（`com.miui.home:string/app_category_games`），
是系统的"自动分类"生成的，内容何时被重排由系统说了算。把用户整理进去的图标交给它保管，
等于让这次整理随时可能被悄悄回滚——所以这类文件夹不复用，删掉重建一个同名普通文件夹。

唯一的例外是里面有**不进整理的东西**（真机「工具」里有个 `itemType=1` 的「查找」入口）：
不删就必须复用，否则桌面上会多出一个空壳文件夹和新文件夹并排站。


### 分析范围是全部图标，不是"散落的几个"

0.7.0 及以前只分析 `container=-100` 的散落图标。问题是：**用户真正想知道的是"我这一屏摆得对不对"，
而不只是"还有什么没收拾"**。0.8.0 把范围扩到桌面上所有应用图标——文件夹内的成员、桌面散落的、
热区（底部固定栏）的，全都过一遍，然后按判定结果分成四类：

| 判定 | 含义 | 界面 |
|---|---|---|
| `LOOSE` | 散落在桌面，有明确去处 | 「需要处理」区，默认勾选 |
| `MOVE` | 已在文件夹里，但别处明显更合适 | 「需要处理」区，**默认不勾** |
| `IN_PLACE` | 已在文件夹里且位置合适 | 折叠成一行「另外 N 个位置合适」，点开可查 |
| `HOTSEAT` | 热区图标，天然是刻意放的 | 同上，不做建议 |

折叠不是偷懒：真机上有 155 个图标，逐行建 `ViewGroup` 展开一次要卡几百毫秒，而这一堆恰好是
不需要动手的部分。

**`MOVE` 的阈值必须比 `LOOSE` 高得多。** 散落图标没得选，指个方向就是帮忙；而劝人把已经放好的
图标搬家是冒犯——用户的文件夹是他长期手工调出来的。所以 `MOVE` 要求别处的分数比当前文件夹高出
`≥ 0.8` 才成立。还有个隐含的保守：算当前文件夹得分时，这个图标的主题本来就算在它自己的画像里，
等于它给自己投了一票，方向也是"别动"。

用真机数据实测（155 个图标 / 18 个文件夹）：**146 个位置合适、4 个散落、1 个认不出、4 个热区，
`MOVE` 判定 0 条**。也就是说这套阈值在这张真实的桌面上不产生任何噪音。

### 怎么判断"该进哪个文件夹"

不预设"银行文件夹里该装什么"，而是**从文件夹里已经装了什么反推它的语义**，得到主题画像，
再拿候选应用的主题去比对。这样用户手工调过的分类习惯会被自动继承。

三路信号加权：

| 信号 | 权重 | 说明 |
|---|---|---|
| 主题覆盖 | 1.0 | 候选应用的主题有几个能在这个文件夹里找到同类 |
| 主题密度 | 0.6 | 命中的主题在该文件夹占多大比例，越"专"的文件夹越可信 |
| 同厂商 | 2.0 | 包名第二段相同，如建行生活 `com.ccb.*` 与"中国建设银行" `com.ccb.*`。一条就够定案 |

主题词典有 18 个主题（银行 / 证券理财 / 购物 / 外卖到店 / 出行交通 / 车服务 / 社交社区 /
影音视频 / 音乐音频 / 办公文档 / 云盘传输 / 学习 / 开发Root / 浏览器 / 影像摄影 / 智能家居 /
系统工具 / 游戏），每个判定都能说出理由，界面上直接显示成
「同属「证券理财」（该文件夹已有 5 个）」。

真机上跑出来的结果：

| 散落图标 | 建议去处 | 依据 |
|---|---|---|
| 短信 | 工具 | 同属「系统工具」（已有 14 个） |
| 同花顺 | 支付·理财 | 同属「证券理财」（已有 5 个） |
| Tesla | 出行 | 同属「车服务」（已有 1 个） |
| 建行生活 | 银行 | 同厂商 `com.ccb` 已在「银行」 |
| Deskly 自己 | 开发·Root | 同属「开发Root」（已有 9 个） |

Deskly 这类 LSPosed 模块本身没有任何能写进词典的关键词。与其往词典里一条条加包名（永远加不全），
不如认它们的共同结构：模块 APK 里一定带着 `META-INF/xposed/` 目录。查到就归入开发类。

### 两个真机踩出来的坑

**短英文关键词不能做子串匹配。** 初版 `nio`（蔚来）直接 `contains` 判断，结果
`com.unionpay` 里恰好含 `nio`（u-**nio**npay），云闪付被判成车服务，Tesla 的归位建议里
凭空多出一个"支付·理财"的次选。现在规则是：**中文词按子串匹配，长度 ≤4 的纯 ASCII 词必须
精确等于包名或应用名切出来的某一段**。`abc` / `boc` / `cmb` / `etc` 都是同一个雷。

**文件夹内的 cellY 不一定等于 cellX/4。** 147 个文件夹成员里有 4 个不满足这个等式
（"个人所得税"存的是 `cellX=7, cellY=2`），因为用户手动拖拽过。所以插入新成员时不能简单
`max(cellX)+1`，要按"序号递增、跳过已占格位"找第一个空位——宁可往后多排一格，
也不覆盖别人的位置。

### 写入流程

```
拍 pre-apply 快照（同时是回滚点）
  → 复制成工作副本 → 只在副本上 UPDATE → 副本 checkpoint(TRUNCATE)
  → force-stop 桌面 → 删 -wal/-shm → cat 副本 > 真库 → sync
  → 比对真库与副本的 sha256，一致才算成功
```

为什么不直接在真库上 UPDATE：桌面进程持有句柄，root 虽然能抢到锁，但桌面内存里的模型
不知道数据变了，它下一次写回就会把改动冲掉；中间态还可能让 WAL 与主库对不上。
整体替换 + 先杀后写，是唯一没有中间态的路径。

应用前还会**重读一次布局**校验每个图标确实还在桌面上——你分析完到点应用之间可能拖过图标，
按旧坐标写就是错的。发现不一致会中止，一个字节都不写。

## 备份与恢复

这一块是整个框架的安全网。设计上只守三条：

| 约束 | 做法 |
|---|---|
| **基线不可变** | 首次运行自动存下 `origin` 快照，之后永不覆盖、永不删除。它就是你口中的"最开始的样子" |
| **写之前先自保** | 整理与归位前存 `pre-apply`；**恢复不再额外备份**（0.12.0 起）——想留退路先手动点一次「备份当前桌面」 |
| **先杀后写** | 先 `am force-stop` 停掉桌面进程，等 1 秒再写文件——launcher 活着时持有句柄，直接写会被它的内存状态覆盖回去 |

### 0.8.0：备份要能"看见"结果

| 改动 | 原因 |
|---|---|
| 按钮「拍快照」→「备份当前桌面」 | "快照"是开发者词汇，说人话就是备份现在这张桌面 |
| 备份完成 → 状态行首行出现绿色回执 `✓ 已备份当前桌面 · 11-03 14:41 · 116 KB（共 3 份）` | 原来只有一个 Toast，一两秒就没了，列表也没变化，用户会怀疑到底存没存。回执带颜色、带份数，直到下次操作才被替换 |
| 失败也回执 `✗ 备份失败 · <原因>` | 失败只在 Toast 里说，划一下屏幕就看不到了 |
| 每份备份右侧一个实心胶囊「恢复」 | 原来是个 12sp 的无底色小字，跟「删除」长得一样重，几乎看不见 |
| **没有 root 也把备份列出来** | 快照存在应用私有目录，列出来不需要 root。以前 `canWrite=false` 时整个列表是空的，等于假装备份不存在。现在恢复按钮压暗但仍可点，点了会解释为什么现在不能恢复 |

恢复按钮不可用时不是静默失效：点它会弹一句「恢复要写回系统数据库，必须先有 root」，
并带上当前 root 探测的结论（没授权 / 守护进程挂了 / 没有 su）。

几个实现上的关键点：

- **WAL 三件套**：`launcher.db` 在 WAL 模式下，只拷主文件会丢掉未 checkpoint 的事务。所以 `-wal` / `-shm` 一起拷。
- **在副本上 checkpoint**：拷到私有目录后，用系统自带的 `SQLiteDatabase` 打开副本，跑 `PRAGMA integrity_check` 并 `wal_checkpoint(TRUNCATE)`。合并之后主库副本自洽，恢复时只需写回一个文件。
- **写回用 `cat >` 而不是 `cp`**：`cat >` 只改内容、保留目标文件的 inode，属主 / 权限 / SELinux 上下文原样不动。用 `cp` 覆盖会把 owner 变成 root，桌面进程直接打不开——那正是要避免的事故。
- **校验**：备份时算 SHA-256 存进 `meta.json`；恢复后用 `sha256sum` 比对，设备上没有这个命令就退化为比大小。
- **保留策略**：`origin` 永久保留，其余最多 8 张，超出按时间淘汰最旧的。

### 选库：一个真机上才会暴露的坑

小米桌面的 `databases/` 目录里同时躺着十来个库：`launcher4x6.db`、`app_category_new.db`、
`onetrack_cache.db`……早先的实现是"名字不认识就取第一个 `.db`"，而 `ls -1` 是字母序，
`app_category_new.db` 排在 `launcher4x6.db` 前面——于是把**分类库**当成了**布局库**。
后果是备份了一份没用的文件、恢复时还写错了地方，而界面上一切正常，这种失败最难排查。

现在三级优先：已知名字 → 任意 `launcher*.db` → 任意 `.db`（先剔掉已知非布局库）。
同一级有多个候选时用一条 `stat` 把体积一次取回、选最大的那个。

> 首次运行拍下的 `origin`，是你**装这个版本时**的桌面状态。如果装之前桌面已经乱了，基线记录的就是乱掉的样子——这一点没法追溯，只能是装好后再手动存一张干净的。

## 两个预设方案

「整理方案」卡片常驻显示（不等分析完成才出现，因为选方案是动手**之前**就该定的事）：

| 方案 | 判定依据 | 分组 |
|---|---|---|
| **方案一 · 按颜色** | 图标 rasterize 到 48×48，剔除近白/近黑/低饱和像素，按饱和度平方加权求主色，再按 HSV 色相分桶 | 红 / 橙 / 黄 / 绿 / 青 / 蓝 / 靛 / 紫 / 粉 / 黑白灰 |
| **方案二 · 按功能** | 精确包名表 → 包名/应用名关键词 → 系统 category，三级判定 | 社交 / 影音 / 游戏 / 购物 / 金融 / 出行 / 办公学习 / 工具 / 生活 / 摄影 / 资讯 / 系统 / 其它 |

选中的方案卡片有三重标记（淡靛底 + 靛色描边 + 左侧竖条），只靠"颜色变深"在浅色主题里对比不够。
每张卡片右侧显示该方案会分出几组——切过一次就记住了，方便直接比较两种方案的粗细。
选择落 `SharedPreferences`（`deskly_plan`），关掉 App 不丢。

按颜色的关键取舍：直接对图标取平均色会得到一片灰，因为绝大多数图标是白底+彩色 logo。
所以采样时做三重剔除（`v>0.94 && s<0.10` 判为白底、`v<0.10` 判为黑、`s<0.16` 判为灰），
再按 `s²` 加权——饱和度越高的像素越可能是 logo 本体而不是底色。

阈值已用主流 App 主色回归验证（微信/支付宝/淘宝/抖音/B站/小红书/京东/美团等 16 例，分桶全对）。

> 0.9.0 时这两个预设方案只是**预览**，真正落地的只有「归位」。0.10.0 起它们直接驱动写入：
> 选中的方案就是整理时执行的分组依据，预览里的屏号就是写进库里的屏号。

## 第一屏留空 · 分组指定屏号 · 分屏布局

勾选「第一屏留空」后，所有文件夹从第二屏开始排，第一屏只留壁纸。这是很多人的实际用法：
第一屏放壁纸和小组件，应用从第二屏开始。

这个开关**不是只存一个布尔值**——它立刻反映到「分屏布局」预览里：

```
分屏布局
共 2 屏 · 9 个文件夹 · 每屏 6 个（4×6 网格，文件夹占 2×2）
┌ 第 1 屏                              留空 ┐   ← 虚线圈，表示"有位置但没内容"
│ 留空 · 一个图标都不放                      │
└──────────────────────────────────────────┘
┌ 第 2 屏                    6 个 · 剩 0 格 ┐
│ 社交 6 · 影音 4 · 游戏 2 · 购物 3 · 金融 5 …  │
└──────────────────────────────────────────────┘
```

### 每屏到底是 24 个还是 6 个

**6 个**。0.5.0 按 4×6=24 位算，是错的：一个文件夹占 2×2 格，所以一屏只装得下
`(4/2)×(6/2)=6` 个文件夹。这个数字不是推测，来自真机
`/data/user_de/0/com.miui.home/databases/launcher4x6.db` 里 175 条记录的实际坐标——
18 个文件夹按每屏 6 个正好铺满 3 屏，剩余散图标才落到后面。

按 24 算的后果是"第 5 屏"的组被摊到第 2、3 屏，预览看起来还有富余，动手时才发现塞不下。

### 分组行上的屏号可直接改

「分组明细」每行右侧有个屏号胶囊：**灰底 = 自动排的，靛底 = 你手动钉的**。点它选屏号，
选「自动」就交回顺序排布。钉屏规则：

- 钉过的组先占位，其余的按原顺序填进剩下的空格
- 勾了「第一屏留空」时，对话框里不出现"第 1 屏"（选了也不生效，等于骗用户点一下）；
  已有的第 1 屏钉屏记录会被一并清掉，免得标签写着"已钉"而实际位置不符
- 钉到已满的屏不拦着，但那一屏会标红「超 N 个」——宁可把冲突显示出来，也不要静默挪走
- 钉屏只影响排布，不触发重新分类，所以改完是立即重画，不会闪一下"正在分组…"

布局算法要点：

- **一个分组 = 一个文件夹**，占 2×2 格。组内应用再多也不拆，文件夹本身可滚动。
- **一屏满了自动开下一屏**，屏号连续。
- 分组为空时不留空屏，但**刻意留空的第一屏必须保留**——否则勾了开关看不到第一屏，会让人以为没生效。

分页逻辑用 Python 复现同一套算法跑过 8 个边界场景（9 组不跨屏 / 9 组留空 / 25 组跨屏 / 25 组留空跨屏 /
48 组整 2 屏 / 0 组 / 1 组），断言"屏号连续、除留空屏外不超容量、留空屏只能在第一屏且必须为空"全部通过；
钉屏分支另外验过"钉到满屏 / 钉到更高屏留空洞 / 留空与钉第 1 屏冲突"三种。

## 三层架构

```
Boot (extends XposedModule)
 └─ Warden          进 launcher 进程后按包名过滤，决定是否接管
     ├─ RuntimeProbe      在真实 classloader 里确认结构类存在（结果进 LSPosed 日志）
     └─ Organizer         写入层，依据探针结果装配 hook

MainActivity (独立进程，不参与注入)
 ├─ DexLister        自己解析 APK 的 classes*.dex，列全部类名
 ├─ ApkInspector     反射 dump 候选类的方法/字段签名
 ├─ AppClassifier    分类引擎（从零分组，用于两个预设方案）
 ├─ PlanSection ── PlanConfig（持久化）＋ LayoutPlan（分屏排布）
 ├─ BackupSection ── Shell(su) ── BackupStore / LauncherDb / Snapshot
 └─ RelocateSection ── DesktopModel（读布局）＋ Semantic / FolderMatcher（出建议）
                       ＋ LayoutWriter（写回）
```

### 为什么还有一条路没走

桌面上的文件夹、图标位置，是 launcher 的私有数据，Android 从来没有开放"建文件夹"的 API。

目前走的是 **root 直改数据库**：停 launcher → 改 `favorites` 表 → 拉起。它的好处是不用探针、
可以先分析再确认、可以强制备份、可以回滚，而且已经跑通了。

没走的是 **hook launcher 进程、调它自己的建夹/移动方法**。这条路一致性好（走它自己的写入流程），
但要求先在真机上探出真实方法签名——`hook("com.miui.home.launcher.FolderInfo", "add")` 这种是猜的，
装上去的结果是 launcher 崩溃 + 桌面重置。等归位这条路积累够真实数据之后再说。

## 明确不走的几条路

| 方案 | 否决原因 |
|---|---|
| 无障碍模拟拖拽 | 坐标/动画时序不稳，Android 14 起还要用户解"受限设置"，Play 直接拒审 |
| 自己写 Launcher | 干净，但要用户换桌面——那是另一个产品 |
| Shizuku | shell 权限对 launcher 私有目录没有读权限，解决不了布局问题 |

## 构建与体积

```bash
export JAVA_HOME=/path/to/jdk17
export ANDROID_HOME=$HOME/Library/Android/sdk
./gradlew assembleRelease     # 交付用这个
./gradlew assembleDebug       # 迭代用，不压缩、可调试
```

`release` 用 `~/.android/debug.keystore` 签名，目的是能和已装的旧包**覆盖升级**（签名一致），
不是发布到任何商店。

### 体积构成（0.9.0 release，68 KB）

| 部分 | 大小 | 说明 |
|---|---|---|
| `classes.dex` | 48.4 KB | **只有 1 个** dex，55 个类 |
| `res/`（布局 + 图标 + 形状） | 7.2 KB | 18 项 |
| `resources.arsc` | 5.0 KB | |
| 签名块（APK Signing Block） | ~7 KB | v2 签名在条目之外，必需，无法省 |
| 模块描述 + 清单 | 0.3 KB | |

0.8.0 → 0.9.0 涨了 1.0 KB（67.0 → 68.0），**没有新增类**：命名空间包装是 `Shell.su()` 里
的一行替换加一个探测方法，选库改造是把 `pick`/`biggest` 换成 `pickAll`/`biggestOf`，
类数量仍是 55。这 1 KB 主要是新增的说明文案与 `LinkedHashMap` 那套解析。

0.7.0 → 0.8.0 涨了 3.0 KB（64.0 → 67.0），只多了一个类，其余是 `RelocateSection` 里
分区渲染那几个方法（分区标题、折叠开关、只读行）和备份回执的文案常量。
分析范围从 5 个图标扩到 155 个**没有带来体积增长**——判定逻辑本来就是全量的，缺的只是遍历入口。

0.6.0 → 0.7.0 涨了 0.4 KB（63.6 → 64.0）：把"root 能不能用"拆成"为什么不能用"只多了一个类
（`Shell$Probe`）和一批文案常量。

0.5.0 → 0.6.0 涨了 2.2 KB（61.4 → 63.6）：拆页面没有加类，只是把布局重排成
「固定头 + 分段 tab + 两个 ScrollView」，代码量几乎没动；增量来自三张新形状
（`bg_tab_track` / `bg_tab_on` / `bg_warn_block`）和钉屏那两个方法的字符串常量。

0.5.0 比 0.4.0 大了 14.6 KB（46.8 → 61.4），全部来自归位这条链路：
`DesktopModel` 读布局、`Semantic` 主题词典、`FolderMatcher` 打分、`LayoutWriter` 写回、
`RelocateSection` 界面，dex 从 29.0 涨到 41.7 KB，仍是单份 dex。

瘦身的两个真实动作：

1. **dex 从 6 个合成 1 个**。AGP 在不启 R8 时会把 `R`、`L`、`Boot` 各自单独打成一个 dex，
   6 个 dex 每个都带完整的 string/type/method 索引池，重复量极大。开 R8 后合并为 1 个。
2. **R8 剔除未引用代码与资源**。`shrinkResources` 实际干掉了 `CardTitle` 样式、
   以及早期版本里两个没用上的 tab 背景。0.6.0 真的用上了 tab，于是又建了
   `bg_tab_track` / `bg_tab_on`——只要是被布局引用的，shrink 就不会删。

代价：R8 会重命名类（`BackupStore → LauncherDb → a.a` 之类，`LayoutPlan` 甚至被整体内联后删除），
所以 `Boot` 必须 `-keep`——它的名字写在 `java_init.list` 里，一旦被改名，LSPosed 加载失败的表现是
「模块已启用但不生效」，极难排查。

> 排查"类是不是丢了"时别只看 dex 里的类名：`LayoutPlan` 在 dex 里根本不存在，但在 `mapping.txt` 里
> 显示为 `R8$$REMOVED$$CLASS$$1`，`usage.txt` 里只有它的 3 个 `static final int` 常量（编译期内联）。
> 真正判定方法是查它的字符串字面量是否还在 dex 里 —— 在，就说明逻辑被内联进调用方了。

> 为什么 debug 包反而比 release 大：debug 不压缩，又回到了 6 个 dex。对外安装一律用 release。

## 已知限制

- 只对 `com.miui.home` 做过默认配置，其它桌面需手动加作用域（`TargetRegistry.isSupportedLauncher` 有兜底判断）
- `AppClassifier` 的精确表覆盖主流国产 App，长尾应用靠关键词，会有误分；它服务的是"预设方案预览"，
  归位用的是另一套 `Semantic` 主题词典，两者刻意没有合并
- 归位会改 `container/screen/cellX/cellY`：散落图标会被放进文件夹；已在文件夹里的（`MOVE`）会被
  搬到另一个文件夹，原来占据的格位会空出来，launcher 可能自行把后面的图标顶上来。**不会新建文件夹**
- 「位置合适」的 140 多个图标默认折叠显示，因为逐行渲染会卡；折叠不代表没分析，点开能看到每一个
  的判定结果和所在文件夹
- 建议可能不符合直觉：短信进了「工具」而不是「社交·社区」，因为你的工具文件夹里已经有「联系人」。
  这类跨类的判断一律可以在界面上点开改目标
- 主题词典对金融、出行、影音这类常见类别覆盖较好，冷门领域的应用会落到"认不出它的类别"，
  这时不会给建议，只留手动选择
- 探针报告的反射部分对依赖系统私有 API 的类会失败，报告中会标注 `[加载失败]`，不影响其余类
- 写入结束后会自动 `input keyevent 3` 把桌面按回前台；若你的 ROM 拦了这条命令，手动按一次 Home 即可
- 分屏布局按 **每屏 6 个文件夹**（4×6 网格、文件夹占 2×2）计算，这个数字取自真机 `launcher4x6.db`
  的实际坐标。你把桌面网格改成 5×6 的话，每屏容量会变，预览的"剩几格"会偏大；
  写入阶段应改为从 launcher 配置读网格，而不是继续用常量
- 钉屏允许把组钉到已满的屏，会有「超 N 个」的红字提示但不拦着——预览阶段就先按用户说的排，
  真要写入时再做冲突消解
- 「第一屏留空」只针对**应用图标**：小组件（如 4×2 的日历）仍留在第 1 屏，不会被搬走。
  它塞不进文件夹，搬走它意味着要另开一屏，收益不如让它待着
- 整理会**重建文件夹结构**：你手工分的"银行 / 支付·理财 / 外卖·到店"这类细粒度分类会被合并成
  方案定义的 11 组。想保住自己的分类就只用下面的「精细归位」；两条路径共用同一份快照机制
- 系统自动分类产生的「工具」「游戏」文件夹（标题是资源引用）会被删掉重建，因为它们的内容
  何时被系统重排不受我们控制
